# RoomEQ code, correctness, performance, and testing audit — 2026-10-18

## Assessment

RoomEQ has substantial defensive engineering and a large, useful test suite. Its strongest evidence is around input validation, individual DSP operations, routing representation, finalization, and export equivalence. The weaker area is the composition of those parts: physical output identity, seat identity, acoustic target reference, and feasible relative delays across advanced subwoofer configurations.

This audit reproduced four correctness defects. Three are in joint multi-sub optimization; the fourth is in home-cinema DBA output mapping. It also identified a missing final acceptance invariant for correlated bass. These are significant enough that passing the current tests is insufficient evidence of correctness for complex multi-sub/home-cinema configurations.

Performance has identifiable avoidable work inside objective evaluation, and the existing home-cinema scaling benchmark does not exercise the most demanding subwoofer paths. Measured joint-stage timings are reported below; no unmeasured speedup is claimed.

| ID | Priority | Finding | Evidence |
| --- | --- | --- | --- |
| C1 | High | Four physical DBA outputs collapse to two in a successful home-cinema result | Full `optimize_room` reproduction and code trace |
| C2 | High | Joint mode returns seat 0 even when another primary seat is configured | Production dispatch reproduction |
| C3 | High | Joint target construction mixes relative target shape with absolute SPL and loses the array level reference | Production dispatch reproduction |
| C4 | High | Fixing the first delay to zero while forbidding negative relative delays makes solvability depend on subwoofer order | Engine reproduction with an analytically solvable fixture |
| C5 | Medium | Final correlated-bass replay reports an advisory, without a cancellation acceptance check | Code-confirmed gap; no escaped final-artifact counterexample demonstrated |
| P1 | Medium | Joint renderer repeats avoidable transcendental work for every seat | Code trace and stage scaling measurements |
| P2 | Medium | Independent route searches evaluate unrelated sources repeatedly | Code trace |
| P3 | Medium | Search budgets have stage-specific floors/caps and inconsistent units | Code trace |

“High” means a supported configuration can have the wrong physical interpretation or lose a known feasible solution. It does not mean every default RoomEQ run is affected, nor that every problematic intermediate candidate survives finalization.

## Correctness findings

### C1 — Home-cinema DBA loses physical outputs when an array has more than one driver per side

**Trigger:** a `SpeakerConfig::Dba` containing two front and two rear measurements, with four declared physical sub outputs referencing that group.

The configuration assembly explicitly counts DBA branches as `front.len() + rear.len()` and accepts the group when that count matches the declared outputs: [`physical_sub_speaker_config`](crates/roomeq-workflow/src/topology/home_cinema.rs), lines 2263–2286.

However, [`preprocess_dba_with_frequency_samples`](crates/roomeq-workflow/src/topology/bass_management/preprocess.rs), lines 616–674, reduces the entire front and rear arrays to exactly two `SubDriverInfo` entries. These contain aggregate array responses, with one control set per array. Home-cinema assembly then zips those two entries against the declared physical outputs at lines 2658–2661 of `home_cinema.rs`. Only the first two output identities survive this operation. [`resolved_bass_sub_outputs`](crates/roomeq-engine/src/home_cinema/resolved.rs), lines 118–127, prefers the nonempty optimized output list over the configured list.

**Observed:** an ordinary public `optimize_room` call with L/R mains and a two-front/two-rear DBA returned success. Its bass-management metadata contained only `["Sub1", "Sub2"]`, although the input declared `Sub1` through `Sub4`. The final routing graph confirmed the loss: its physical sub list was `["Sub1", "Sub2"]` and its complete output list was `["L", "R", "Sub1", "Sub2"]`. A one-front/one-rear control case also succeeded with two outputs, as expected. This is a topology cardinality error, independent of whether the synthetic room response is realistic.

**Consequence:** the workflow conflates an array-level optimization variable with a physical output. For a front-first physical ordering, the rear array's control can also be assigned the identity of the second front driver. A successful return must not silently redefine the declared hardware topology.

**Repair:** maintain a separate mapping from the two optimized array controls to every physical driver. Expand the front control across all front outputs and the rear control across all rear outputs, while retaining each driver's own measured transfer function. If only two externally summed array outputs are supported, validate and represent that explicitly; do not accept four outputs and return two.

**Required regression:** two-front/two-rear and asymmetric two-front/three-rear fixtures. Assert exact output identity/cardinality through configuration, preprocessing, routing graph, serialized export, and replay. Excite each logical input and verify that every declared physical branch exists and carries the intended front/rear control. The current preprocessing happy-path test covers only one front and one rear driver, which cannot expose this mismatch.

### C2 — Joint multi-sub dispatch ignores the configured primary seat

[`process_joint_sub_group`](crates/roomeq-engine/src/multisub/joint_objective.rs), line 888, assigns `result.per_seat_post.first()` to `primary_seat_complex`. It does not select `optimizer.multi_seat.primary_seat`.

This field is consequential: [`MultiSubCombinedResponse`](crates/roomeq-engine/src/multisub/types.rs), lines 27–39, separates the spatial magnitude from the coherent primary-seat response. Group processing consumes that primary response, and home-cinema processing uses a configured primary seat for the mains. Combining the complex response of a main at one seat with that of a sub array at another seat has no valid same-position acoustic interpretation.

**Reproduction:** two subs, two seats, 128 logarithmic bins from 20–160 Hz. Each sub is 80 dB/0° at seat 0 and 90 dB/90° at seat 1; `primary_seat = 1`. The production joint dispatch returned, at the first bin:

| Quantity | SPL | Phase |
| --- | ---: | ---: |
| Returned `primary_seat_complex` | 86.0206 dB | 0° |
| Rendered seat 0 | 86.0206 dB | 0° |
| Requested seat 1 | 96.0206 dB | 90° |

The stage returned successfully. This demonstrates the wrong seat at the dispatch boundary; it does not establish that all downstream acceptance checks let the resulting error through.

**Repair/test:** select and bounds-check the configured primary index. Add a seat-permutation test that remaps `primary_seat` and requires the same physical result. Include a home-cinema fixture with different main/sub phase at different seats and verify same-seat crossover replay. Relevant consumers include `group_processing.rs` around lines 1144 and 1290, and workflow `topology/bass_management/preprocess.rs` around lines 232–339.

### C3 — Joint target construction does not preserve a consistent acoustic reference

In [`joint_objective.rs`](crates/roomeq-engine/src/multisub/joint_objective.rs), lines 820–840:

1. With a target tilt, its SPL values are passed directly to the absolute joint objective.
2. Without a tilt, the target is the arithmetic mean of individual sub/seat SPL values, rather than the level of the combined array.

[`build_target_tilt_curve`](crates/roomeq-engine/src/channel_target.rs) and [`target_tilt.rs`](crates/roomeq-model/src/target_tilt.rs) construct a relative shape around a reference frequency. That shape is not an absolute measured SPL target. Conversely, two identical coherent 80 dB subs produce 86.0206 dB, not the 80 dB individual-response average used by the fallback.

The absolute target-error term in [`joint_multisub.rs`](crates/autoeq-optim/src/loss/joint_multisub.rs), lines 167–194, therefore rewards a change in acoustic output that is not simply response flattening. The output penalty does not eliminate the problem: it uses the fixed measured power-sum reference, with tolerances, rather than preserving the initial coherent array output.

**Reproduction through production dispatch:** two already aligned, flat 80 dB subs at two identical seats; 128 bins, 20–160 Hz, 48 kHz, DE, seed 7, 300 generations, population setting 30, gains bounded to ±12 dB.

| Target configuration | Initial combined mean | Final combined mean | Objective before → after | Returned controls |
| --- | ---: | ---: | --- | --- |
| Default | 86.0206 dB | 80.9432 dB | 36.2476 → 1.95524 | Gains `[0, -12]` dB; delays `[0, 2.50618]` ms |
| Custom slope −0.5 dB/octave | 86.0206 dB | 78.0676 dB | 7047.57 → 5853.24 | Gains `[0, -0.759576]` dB; delays `[0, 16.6679]` ms |

The default case sacrifices about 5.08 dB from an already aligned flat array while improving the objective. The custom case also illustrates the absolute-reference mismatch. These are intermediate stage observations: shared EQ and final safeguards may change or reject them. They still represent unnecessary cancellation/output loss and a misleading optimization target upstream.

**Repair:** define an explicit acoustic level reference for the combined baseline, then apply the relative tilt to that reference. Decide whether the array stage owns absolute level or only response shape/output efficiency, and encode that distinction in the objective. Preserve output efficiency independently of a target-level adjustment.

**Required regressions:** aligned flat arrays with two and four subs; equivalence between a flat target and a zero-slope custom target; common SPL-offset invariance when the physical task is unchanged; and final delivered output/headroom checks after shared EQ. Existing objective fixtures that supply an absolute 86 dB target directly do not exercise this dispatch bug.

### C4 — Delay bounds make the joint optimizer depend on subwoofer ordering

[`joint_objective.rs`](crates/roomeq-engine/src/multisub/joint_objective.rs), lines 485–494, gives every delay a `[0, 20]` ms range and fixes the first sub's delay to zero. Removing a common delay is valid only if the remaining relative-delay parameterization still represents all admissible solutions. This one does not.

Consider two measured arrivals at 0 and 4 ms. The causal alignment is to add 4 ms to the first sub and 0 ms to the second. The current bounds forbid it. Reordering the identical physical system to put the later arrival first makes the solution available.

**Reproduction:** flat 80 dB responses with linear phase corresponding to those arrivals; two seats; 128 bins over 20–160 Hz; gains fixed to 0 dB; absolute coherent target 86.0206 dB; DE seed 7, 300 generations, population setting 30.

| Measurement order | Optimized added delays | Final loss | Array rejection reason |
| --- | --- | ---: | --- |
| `[0 ms, 4 ms]` | `[0, 0.0275502]` ms | 102.1645 | None |
| `[4 ms, 0 ms]` | `[0, 4.000606]` ms | approximately 2.0e−14 | None |

This is a feasible-set error, not merely an unlucky stochastic result: the missing optimum is algebraically excluded in the first ordering.

**Repair:** use signed relative delays with a well-defined normalization to causal physical delays, or optimize all bounded nonnegative delays and remove a common minimum afterward. Account for the resulting common latency consistently in main/sub alignment and export. Ensure the normalized solution respects physical delay limits.

**Required regression:** permute physical sub order and remap output identities, then compare acoustic responses and achievable loss. Cover positive and negative relative arrival differences and more than two subs. Existing tests that assert first-delay-equals-zero reinforce the representation without establishing its completeness.

### C5 — Final correlated-bass assessment is informational, not an acceptance condition

Home-cinema route refinement gives each source independent delay, polarity, and trim variables: [`bass_management/optimize.rs`](crates/roomeq-engine/src/bass_management/optimize.rs), lines 2119–2192. Individually good main/sub sums do not imply a good result when correlated bass is present on multiple program channels.

[`assess_mono_bass_sums`](crates/roomeq-workflow/src/room_optimization/seat_replay.rs), lines 789–857, computes peak coherent level and the **maximum** buildup relative to a power sum. It does not measure the worst cancellation or a baseline-relative loss of correlated output. A maximum cannot characterize a deep dip elsewhere in the band.

`correlated_bass_stage`, lines 866–939, replays training seat 0, emits `Applied` with an empty `checks` list on success, and emits a skip/advisory on replay failure. [`finalization.rs`](crates/roomeq-workflow/src/room_optimization/finalization.rs), lines 784–794, appends this stage after selection of a successful result. It cannot reject that result.

There are useful separate safeguards: electrical headroom checks, stereo-specific serialized candidate checks, and correlated conditions in pruning. Those do not establish a final, multi-seat correlated acoustic acceptance invariant for the home-cinema route optimizer.

**Recommendation:** replay declared correlated groups, including L=R and L=C=R where applicable, through the final serialized graph at relevant seats. Compare cancellation/output efficiency against a protected baseline, while retaining electrical peak/headroom checks. Make any intentionally unassessed case explicit in the final acceptance state. This audit establishes the missing guard; it does not demonstrate a particular bad final artifact escaping all other guards.

## Performance audit

### Measured joint-stage scaling

Release builds; five fresh-process repetitions after the long audit test suites and Criterion run had stopped. These are wall-clock observations on a developer machine, without CPU pinning or a controlled thermal environment.

Fixture: flat complex responses, delay of `0.5 * sub_index` ms, identical seats, 20–160 Hz, 48 kHz, coherent absolute target, DE seed 7, `max_iter = 10`, population setting 20, zero stopping tolerances, gain bounds ±3 dB. Timed region is `optimize_joint_sub_array`, excluding input generation, compilation, I/O, shared EQ, home-cinema routing, and export.

| ---: | ---: | ---: | ---: | ---: |

### P1 — Avoid repeated polar reconstruction inside the joint objective

[`render_combined_field`](crates/roomeq-engine/src/multisub/joint_objective.rs), lines 181–208, already receives complex measurement responses. For every evaluation, seat, frequency, and sub it computes gain conversion, complex norm, complex argument, and a polar reconstruction. The measured response and the sub controls are repeatedly decomposed and rebuilt.

The same field can be calculated as:

`H[seat, sub, f] * 10^(gain[sub]/20) * exp(-j * 2π * f * delay[sub])`.

Precompute the control multiplier once per sub/frequency for each candidate, then multiply the cached complex measurements at each seat. Reuse field/level scratch buffers where ownership permits. This removes repeated norm/argument work and makes control transcendental cost independent of seat count. The current code already restricts the optimization band; retaining that is important.

Validate equivalence with nonzero measured phase, nonzero delays, cancellation, irregular grids, and multi-seat inputs. No replacement was implemented or benchmarked in this audit, so there is no claimed speedup percentage.

### P2 — Per-source route searches recompute all sources

In [`bass_management/optimize.rs`](crates/roomeq-engine/src/bass_management/optimize.rs), lines 1977–2080, the evaluator constructs responses and losses for the group's sources. At lines 2151–2177, the objective for one independent source calls that whole evaluator, then extracts only that source's loss and underfill.

For a group containing C sources, this does roughly C sources' evaluation work per one-source objective call. Across all source searches, this can produce work proportional to C² for a fixed per-source evaluation count. Actual total scaling also depends on budget division and minimum populations, so C² is not a claim about measured whole-pipeline runtime.

Factor out a one-source evaluator. Cache fixed shared crossover/sub responses during the independent route stage. Run the complete group evaluator for shared-variable search and final acceptance. Preserve the current final group checks. Main and sub pre-EQ already have Rayon parallelism in the workflow; simply adding more threads is not the primary opportunity identified here.

### P3 — Budget semantics make latency and convergence hard to predict

[`bass_management/misc.rs`](crates/roomeq-engine/src/bass_management/misc.rs), lines 18–124, implements a local DE loop. Population is clamped to 12–96, with a dimension-dependent minimum. Its evaluation budget is raised to at least four populations and capped at 2,000. Group/source allocation divides the requested budget, but each invocation reapplies these floors. Consequently, small requested budgets do not impose a correspondingly small total route-search budget, and large requested budgets eventually stop increasing this stage's effort.

The generic scalar optimizer uses backend-dependent budget semantics; DE `max_iter` is generations, whereas other backends use evaluation-like limits. The joint dispatch passes the generic configuration through, while the route helper always runs its local DE. The joint call also uses the non-callback scalar entry point. These are important operational differences when interpreting a global optimizer configuration, progress, or cancellation responsiveness.

Record actual objective calls, elapsed time, termination reason, and effective budget per stage. Separate generation and evaluation limits in the configuration/telemetry, and propagate cancellation to long-running stage searches. Test budget floors and ceilings explicitly rather than inferring work from `max_iter` alone.

### Existing performance coverage misses the demanding path

[`end_to_end_scaling.rs`](crates/roomeq-workflow/benches/end_to_end_scaling.rs) benchmarks a useful fixed-seed 5.1.4 workload and a no-sub variant. Its sub fixture has one sub, one seat, a 20 Hz crossover, 200 frequency bins, and in-memory phase curves without verified capture timing provenance. The workflow's timing-reference checks gate coherent crossover optimization, so this fixture does not establish scaling of the verified phase-aware crossover/route search. It also cannot characterize multi-sub array or multi-seat cost.

Retain that benchmark, but add fixtures with verified timing provenance, two/four/eight subs, several seats, ordinary crossover frequencies, per-sub crossovers, DBA, and realistic hybrid/FIR lengths. Assert that the intended stage actually ran; a fast skipped or reverted stage is not a performance result for that feature. Measure objective counts, stage timings, allocations/peak memory, and final acoustic quality together.

The QA recipes do contain broad acoustic time/memory gates, including 900,000 ms and 4 GiB limits in `builds/qa/qa-roomeq.just`. The gap is representative, stage-specific performance coverage, not an absence of any resource limits. This audit did not measure allocation counts or peak resident memory.

## Quality of testing

### What is strong

- Broad negative tests cover malformed grids, missing/mismatched phase and timing provenance, incompatible configuration, and nonfinite data. These are meaningful protections for coherent processing.
- Tests cover route ownership, delay/polarity propagation, finalization and fallback behavior, seat constraints, and deterministic fixed-seed behavior, including one-versus-four-worker home-cinema runs.
- Export tests in [`realized_transfer.rs`](crates/roomeq-export/src/tests/realized_transfer.rs) parse emitted representations and compare transfer behavior, with analytic anchors and opt-in external backend checks. This is stronger than merely comparing serialized strings.
- The coverage gate targets all six production RoomEQ crates, plus integration tests; it is not confined to the root compatibility facade. `builds/qa/qa-roomeq.just`, lines 227–235, specifies a 90% library line-coverage threshold. This audit inspected the gate but did not collect coverage or verify the checkout's current percentage.
- The repository includes subsystem/mutation checks, independent mathematical golden fixtures, CI backend integration, and acoustic/FEM work. Their presence is relevant evidence of test design, but is not equivalent to having run them during this audit.

### Where the evidence is weaker

**Component-level oracles do not cover composition.** The Wolfram joint-objective fixture in `crates/autoeq-qa/tests/wolfram_o08_joint_multisub.rs` independently checks scalarization from supplied seat levels. It does not execute production target construction, choose the primary seat, or prove that delay bounds can represent the optimum. That explains how the objective can have a correct mathematical oracle while C2–C4 remain undetected.

**Small fixtures hide structural errors.** One front plus one rear DBA makes array count equal physical-output count. Flat/constant-phase, few-bin joint fixtures do not strongly exercise broadband delay feasibility. Primary seat 0 makes a hardcoded `.first()` appear correct.

**Improvement of the implemented objective is not an independent physical oracle.** A test that asserts `post_objective <= pre_objective` can pass when the target reference itself is wrong. Require physical invariants: output identity, same-seat phase, permutation invariance, known feasible alignment, and preservation of an already-correct response.

**Safe fallback and successful optimization need separate scores.** The quick home-cinema QA registry permits safe revert for its safety cases (`crates/roomeq-qa/src/coverage/home_cinema.rs`, around lines 95–118). Budget/filter-count comparisons in `crates/roomeq-qa/src/coverage/run.rs` are conditional on convergence/non-reversion. That is appropriate for safety testing, but those successes do not demonstrate that the requested feature optimized successfully. Add known-solvable quality cases in which a revert or skipped stage fails the quality expectation, while keeping separate safety cases where revert is the correct outcome.

**Actuator efficiency deserves a clearer oracle.** The joint `output_drive` term is based on combined acoustic levels relative to a fixed measured power reference. It is not a direct per-driver electrical effort/excursion model. Different combinations of large, mutually cancelling branch signals can have similar acoustic sums. Existing gain bounds and downstream electrical checks are valuable, but tests should not treat the acoustic penalty as proof of physical drive efficiency.

## Recommended order of work

1. Fix the DBA physical-output mapping and add exported-graph cardinality/identity assertions. This issue is reproduced through the public room workflow.
2. Fix joint primary-seat selection, target anchoring, and the delay feasible set together with independent invariant tests. These are fundamental input/output semantics, not optimizer tuning issues.
3. Add end-to-end joint-mode home-cinema fixtures with verified timing, multiple seats, nonzero primary seat, different arrival times, and multiple physical sub outputs. Require a successful intended stage and verify delivered transfer behavior after serialization.
4. Define a final correlated-bass acceptance policy and distinguish assessed, skipped, reverted, and quality-improved outcomes in QA.
5. Optimize the joint renderer and source-specific route evaluator against representative benchmarks. Keep acoustic equivalence and quality checks beside timing measurements.
6. Make actual search effort and cancellation behavior observable before changing default iteration budgets.
